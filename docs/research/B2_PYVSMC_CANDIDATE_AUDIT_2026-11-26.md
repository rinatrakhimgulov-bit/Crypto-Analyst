## 1. Что проект предоставляет

README описывает NumPy/Numba + Polars библиотеку Smart Money Concepts:
- fractal swing highs/lows;
- BOS/CHOCH;
- Fair Value Gaps;
- Order Blocks и breaker zones;
- equal highs/lows и liquidity sweeps;
- Premium/Discount и OTE зоны.

Проект заявляет 92 теста, strict mypy и Ruff. Эти тесты в рамках данного аудита не запускались; заявление README не считается независимым подтверждением качества.

Лицензия MIT. Это допускает использование и модификацию при сохранении уведомления об авторских правах и текста лицензии в распространяемых копиях/существенных частях.

## 3. Критическая проблема: look-ahead в detect_structure

В `src/pyvsmc/swings.py`:
- `detect_swings(high, low, window_size=N)` отмечает swing в исходном индексе `i`, если он является экстремумом в симметричном окне `[i-N, i+N]`.
- Следовательно, swing на баре `i` можно подтвердить только после закрытия бара `i+N`.
- Возвращаемый `SwingResult` содержит boolean mask и цену на pivot index, но не отдельный `confirmed_at` / confirmation index.

В `src/pyvsmc/structure.py`:
- `detect_structure()` вызывает `detect_swings()` и получает маски с отметкой в pivot index.
- Затем `_forward_fill_last_swing()` переносит последний swing level вперёд.
- В строках около 202–210 forward-filled маска сдвигается только на один индекс, чтобы исключить использование swing на самом баре pivot.
- Поэтому новый pivot может стать доступным структуре уже на следующем баре `i+1`, хотя для подтверждения ему требуются `N` правых баров. При N>1 это преждевременно на N-1 баров.

Это потенциальная утечка будущих данных в исторических BOS/CHOCH событиях и трендовом состоянии. Комментарий проекта о предотвращении look-ahead решает только self-trigger на самом pivot bar, но не задержку фактического подтверждения fractal pivot.

### Требуемая коррекция для нашего использования

Нельзя просто принимать `detect_structure()` как есть. Варианты:
1. Формировать confirmed swing event на индексе `i+N`, сохраняя исходный `pivot_index=i` и `confirmed_index=i+N`.
2. В structure engine разрешать использование уровня только начиная с бара после фактического подтверждения, по строго определённому close-time правилу.
3. В историческом replay/backtest событие BOS/CHOCH датировать временем, когда информация реально стала доступна, а не pivot timestamp.
4. Добавить тест на prefix invariance: результат/события, рассчитанные на данных до момента T, не должны изменяться от добавления свечей после T, кроме событий, которые по определению ещё не были подтверждены к T.
5. Сравнить batch calculation и bar-by-bar online calculation; события и timestamps должны совпадать.

## 4. Дополнительные замечания

### Tie/plateau semantics
В текущей версии README указывает default `tie="all"`. При одинаковых high/low все внутренние бары flat-окна могут маркироваться как swing; README прямо описывает это как legacy поведение. `tie="first"` или `tie="strict"` уменьшают множественные экстремумы, но выбор должен быть частью нашей формальной спецификации, а не слепым переключением параметра.

### BOS/CHOCH semantics
Классификация зависит от состояния тренда: первый break устанавливает направление; встречный break трактуется как CHOCH и переворачивает тренд. Если оба направления пробиты на одном баре при нейтральном состоянии, код выбирает bullish BOS по умолчанию. Это правило произвольное для реального рыночного бара и требует отдельной политики (скорее ambiguity/unknown, а не автоматическое предпочтение LONG).

Также нужно проверить, действительно ли каждый break использует актуальный структурный уровень и не повторяет событие после смены уровня/повторного пересечения. Тесты должны покрывать gap-through, wick-only, close-only, equal-level, simultaneous breaks и missing bars.

### Packaging discrepancy
README описывает Polars как optional dependency, однако `pyproject.toml` включает `polars>=0.20.0` в обязательный `project.dependencies`. Это нужно уточнить перед установкой/включением библиотеки. NumPy обязателен; Numba заявлен как optional accelerator.

### Language / integration
Библиотека написана на Python и зависит от NumPy/Polars. Для текущего single-file HTML напрямую не интегрируется. Это не причина отклонять математику: можно либо перенести исправленную реализацию на JavaScript/TypeScript с тестами на одинаковых fixtures, либо позже вынести аналитическое ядро в Python backend. Решение о миграции языка пока не принимается.
